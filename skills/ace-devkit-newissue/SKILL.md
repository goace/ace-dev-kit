# Ace DevKit New Issue

按以下顺序执行。开始或恢复工作时，必须完整阅读 [访谈规范](references/interview-guidelines.md) 和 [知识库维护](../shared/knowledge-base/knowledge-maintenance.md)。需求与设计阶段的知识库维护及整体确认遵循下文共用规则；进入实施后由实施技能负责其维护时机与收尾。

## 1. Issue 理解

进入本阶段时，必须完整阅读 [Issue 理解](references/issue-understanding.md)，按其中的范围开展访谈并整理 `requirements.md`。

满足该文件的完成标准，且用户整体确认需求文档后，才进入第二步。

## 2. 技术方案设计

进入本阶段时，必须完整阅读 [技术方案设计](references/technical-design.md)，以已确认的需求文档为依据完成设计并按需访谈，整理同一 issue 目录下的 `design.md`。

满足该文件的完成标准，且用户整体确认设计文档后，完成本次文档交付。

## 3. 实施与交付

向用户确认是否进入实施阶段。如果进入，则调用 `$ace-devkit-implement` 技能，开始实施。

## 文档阶段的知识库维护

本节及下节只适用于 Issue 理解和技术方案设计两个文档阶段。维护重点与局部完成条件由各阶段参考文档规定。

术语含义明确后，按共享规范即时更新 `GLOSSARY.md`。ADR 候选写入当前阶段文档，随阶段成果整体确认；确认后按共享规范写入正式 ADR，无需再单独请求创建确认。

`requirements.md` 和 `design.md` 各自包含 `知识库变更`：本阶段术语变更摘要、候选或已创建的 ADR、受影响的既有 ADR，以及实际文件链接；没有变更时写“无”。候选明确标为候选，正式定义与已接受决策以知识库文件为准。暂未解决的术语分歧留在当前阶段文档的 `待解决问题` 中。

## 阶段成果确认

两个文档阶段按以下顺序收尾：

1. 将讨论结论整理到该阶段文档，状态标为 `draft`。文档详略随 issue 规模调整，小 issue 也保留两份文档。
2. 对照用户已确认的结论和阶段完成标准自查，检查遗漏、矛盾、歧义和范围扩张。阶段知识库对账包括术语是否遗漏或冲突、ADR 候选及既有 ADR 的影响是否处理。候选明确为待本阶段确认、已否决或已延期；延期项注明原因、影响和后续处理时机，并满足当前阶段完成标准。涉及用户决策的问题回到访谈处理。阶段另有独立检查要求时，在提交整体确认前完成；检查引发的修订重新自查并对账。
3. 提供文档路径和成果摘要，将知识库变更及候选 ADR 一并交给用户做一次整体确认，重点检查遗漏和理解偏差。讨论中已经确定的决策不重复逐项审核，也不逐节索要批准。
4. 用户提出修改时，更新受影响内容、自查并再次提交整体确认。用户明确认可当前文档后，才将状态改为 `confirmed`；沉默或只回答了部分问题均不代表整体确认。
5. 应用本阶段通过的 ADR，按共享规范完成写入核验，回填阶段文档的实际文件链接与处理结果。满足该阶段完成标准后，才结束本阶段。

已确认文档发生实质变更时，将受影响文档恢复为 `draft`，重新确认变化部分；未受影响的结论继续沿用。
