# 技术方案设计

以已确认的 `requirements.md` 为依据形成高层技术方案，对需要用户参与决策的问题按需访谈，最后提交完整方案供用户整体审核。

进入或恢复本阶段时，在形成、比较或修订方案前，必须完整阅读[代码库设计参考](../../shared/codebase-design/codebase-design.md)。将其中适用的规则用于方案设计和自查，结论融入下述高层方案内容；不新增逐条规则汇报、访谈或确认环节。

## 工作流程

### 1. 现状调研

开始本阶段调研前，完整阅读并遵循[现状调研规范](investigation-guidelines.md)。

- 目的：基于已确认需求判断实现路径，为方向性取舍提供依据。
- 范围：需求涉及的模块、调用关系、技术栈、数据存储、现有测试和关键技术约束，重点补查需求阶段带入的可行性问题。
- 程度：足以支撑候选方案、明确修改范围，并查证影响方案成立的关键假设。调查可以深入实现细节，提交给用户的讨论与文档保持下述方案内容的粒度。

### 2. 访谈范围

先根据调研结果作出判断，再筛选需要用户参与决策的问题：

- 已确认需求、项目模式和调查证据足以支持明确选择时，由 agent 直接形成设计，写入方案并说明必要理由。
- 缺少可查明的技术事实时，由 agent 继续调查或验证。
- 调查后仍存在影响方案的实质取舍，无法依据现有信息明确选择，或选择依赖尚未明确的用户偏好和优先级时，提交访谈。
- 需要改变已确认的需求、范围或决定时，按文末变更规则讨论受影响部分。

信心应建立在需求、约束和证据上。存在多个可行方案本身不构成提问理由；能明确解释为什么某个方案更适合当前项目时，可以直接采用它形成设计。需求中写明“技术阶段确定”只表示事项应在本阶段落地，不表示必须由用户逐项选择；用户没有额外偏好时，按已确认目标、约束和现有模式排序并采用推荐方案。

只有多个候选都满足已确认的需求和约束，且它们之间的取舍确实依赖用户偏好或优先级时，才把取舍交给用户。若只有一个候选满足要求，或其他候选明显无法满足需求、引入无必要的复杂度，则由 agent 直接选择并说明理由，不把它包装成用户决策。

每轮收到用户答复后，先根据新结论自主推进设计，再按上述标准筛选后续问题；留待技术阶段确定的事项，也只有符合访谈条件时才交给用户。

只有筛选出的待决问题进入访谈决策树，按共用访谈规范提出全部 frontier 问题。没有待决问题时，直接整理设计并请求整体确认，无需安排一轮形式上的技术问答。Agent 自主形成的设计仍是待用户整体审核的方案。

#### 比较与推荐

存在需要用户决策的方向性取舍时，按以下方式比较候选方案：

- Propose 2-3 different approaches with trade-offs
- Present options conversationally with your recommendation and reasoning
- Lead with your recommended option and explain why

### 3. 设计文档

#### 方案内容与粒度

完整方案覆盖以下适用维度，包括 agent 自主作出的设计和访谈确定的结论；访谈问题仍按上文“访谈范围”筛选：

- 技术选型：技术、框架和关键依赖。
- 模块划分：修改哪些已有模块、新增哪些模块，各自承担什么职责。
- 代码组织：主要目录结构和文件如何组织。
- 主要流程：核心流程、模块协作以及数据流转。
- 涉及数据存储时：持久化数据模型、DB 表结构，包括字段及含义、表之间的关系、主键和关键约束，以及对已有数据的影响。
- 异常处理：影响需求满足或系统正确性的重要失败情形、处理原则及预期结果；涉及跨模块协作或持久化状态时，说明失败对相关流程和状态的影响。
- 验证策略：根据风险说明关键行为、重要异常及受影响现有行为的验证方式，以及必要的验证条件。

函数拆分、具体接口签名、局部算法、具体测试用例和测试代码等实现细节由 agent 自主决定。模块间的重要行为约定、异常处理原则和验证策略属于方案内容，按上述粒度明确。代码内部的数据结构通常也由 agent 决定；非常重要且反直觉的结构需要在方案中突出解释其理由和影响，是否需要访谈仍按上述筛选标准判断。

#### 整理与提交

将设计写入与 `requirements.md` 同目录的 `design.md`，包含 issue ID、标题、状态和需求文档链接。记录适用的设计内容，以及关键选择的理由和取舍；不适用的部分简要标明，不填充无关章节。

各部分篇幅随复杂度调整：简单内容用几句话说明，复杂内容可展开至约 200–300 词。

对照需求中的预期行为、约束和验收条件，说明方案如何满足它们以及如何验证关键假设。结合已加载的代码库设计参考自查，检查结构改进是否有依据且服务于当前目标、重要异常及验证方式是否遗漏，以及关键选择的理由是否与需求和调查证据一致。

本阶段统一按入口的[阶段成果确认](../SKILL.md#阶段成果确认)流程收尾。在自查和阶段知识库对账之后、提交用户整体确认之前，完成下述[交接检查](#交接检查)。

#### 交接检查

每份 `design.md` 都须在用户整体确认前完成独立交接检查，判断未参与讨论的实现者是否仍需猜测会影响实施的重要事项。

自查和阶段知识库对账完成后，完整阅读[交接检查提示词](builder-check-prompt.md)，填写实际路径，交给不继承本次讨论历史的新 subagent。输入为已确认的 `requirements.md`、当前待审核的 `design.md` 和项目目录；检查者可读取相关代码、`GLOSSARY.md` 和 ADR。不提供聊天记录或主 agent 的口头补充；已有讨论结论应通过文档交接。检查者只读材料、向主 agent 返回问题，不编写实施计划、不修改文件，也不直接向用户提问。

主 agent 按以下三类处理反馈：

- **Answered already** by the conversation or the project: put the answer in the document.
- **Minor:** a sensible builder could settle it without changing what gets built. Settle it yourself and mark it in the document as your call.
- **Theirs:** only your human partner can answer it, and the answer changes what gets built.

已有答案先核实再补入相应文档；自主选择按本阶段粒度记录及说明必要理由；只有用户能决定的问题按现有访谈规则处理。涉及已确认需求变化时，按[需求与设计变更](#需求与设计变更)规则返回 Issue 理解阶段。措辞偏好、明确留给实现者的细节等不符合检查范围的问题，可以说明理由后不采纳。

尚未处理的问题记录在 `design.md` 的 `待解决问题` 中；解决后将结论归入相应设计内容，更新问题处理结果。检查引发的修订重新自查；涉及术语或 ADR 的变化，重新核对受影响的术语、ADR 候选及既有 ADR，并更新本阶段的知识库变更记录。

补写已有结论或澄清局部表达后，由主 agent 核对问题是否解决。若修订改变关键技术方向、模块关系、重要行为或约束，再由不继承讨论历史的新 subagent 检查受影响内容。用户整体审核或后续返工提出上述实质性修改时，同样重新触发检查。

独立检查已经返回，影响实施的重要问题均有处理结果、没有未解决的重要问题，且修订后的文档已完成自查与知识库对账后，交接检查完成。按问题及其影响判断是否完成，不要求反复调用直到检查者输出固定的通过字样；需要用户决定的问题继续按现有访谈规则收敛，不限定为一轮。

#### 完成标准

以下条件全部满足时，本阶段完成：设计已覆盖确认的需求；关键技术方向已确定；影响方案成立的技术假设已有调查或验证依据；影响这些决定的待解决问题均已处理；设计文档已完成自查、阶段知识库对账和交接检查；用户已整体确认当前文档，状态为 `confirmed`；本阶段通过的 ADR 已写入并核验，文档中的实际文件链接及处理结果已回填。

## 贯穿规则

### 方案设计原则

以下原则贯穿本阶段的方案形成、比较与修订。

- 优先沿用现有模式；是否调整按共享设计参考和当前目标判断。
- 现有职责划分、模块边界或代码组织问题影响本次工作时，将针对性改进纳入设计，说明问题依据、改进理由及影响范围。改进程度以支持当前目标为限。
- Don't propose unrelated refactoring. Stay focused on what serves the current goal.
- 对影响整体方向的重要技术选择，先考虑实际可行的替代路径，依据已确认目标、约束、项目现状及成本进行筛选。候选探索的深度随选择的重要性和不确定性调整；不为明显选择凑足固定数量的方案。是否向用户展示比较或提问，仍按访谈范围判断。
- YAGNI ruthlessly - remove unnecessary features from every approach and design

### 知识库维护

方案比较和设计调整时，按[知识库维护](../../shared/knowledge-base/knowledge-maintenance.md)核对模块职责、数据关系与已有 ADR；有冲突时说明沿用或替代的理由。澄清新出现的领域术语，甄别需要保存为 ADR 的方向性取舍。

在 `design.md` 的 `知识库变更` 部分按入口的[文档阶段维护规则](../SKILL.md#文档阶段的知识库维护)只记录设计阶段的摘要、候选及文件链接，无变更时写“无”。收尾时核对方案取舍是否遗漏候选 ADR，既有决策是否需要替代，并明确设计与尚未修改的代码之间的差异。

### 需求与设计变更

方案若要求改变需求、范围或验收条件，明确说明原因及影响，返回[Issue 理解阶段](issue-understanding.md)修订并重新确认需求；需求重新确认后，更新受影响的设计。

需要改变已确认的技术方向，或用户在整体审核时对某项设计提出异议时，在本阶段讨论和修订受影响部分，保留其余结论。设计更新或修订后，回到本文件的[整理与提交](#整理与提交)重新收尾；交接检查按修订影响决定是否重新委派。
